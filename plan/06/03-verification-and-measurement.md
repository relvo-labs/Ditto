# G4 驗證與量測

本檔適用 `ditto-verification-evidence`。量測方法、條件與門檻以 [milestones/01/04](../../milestones/01/04-verification.md) 與 PRD §19 為準，本檔只安排 G4 的執行方式。

## 1. 證據環境

| 證據 | 可用於 | 不可用於 |
| --- | --- | --- |
| 實體參考機（通過 preflight，`evidence_class=reference-machine`） | 所有出口，包含 NFR 與 AT-25 | — |
| 實體座位人工操作（owner 或測試者） | 中文輸入、雙螢幕、錄影、使用者測試、SDK 可用性 | 取代自動化量測數字 |
| 開發 VM（`tools/dev-vm`，`evidence_class=development-vm`） | 第一線自動化：含圖形流程的功能回歸、故障注入、安裝流程與長跑練跑，標示實際覆蓋範圍 | 代替實體參考機的圖形、輸入、效能、動畫或資源出口證據 |
| 開發機／headless | 矩陣指定的單元、契約、元件與非圖形安全檢查；可支援對應功能的證據鏈 | 單憑此類結果宣告需要實體座位、完整端到端或量測的出口通過 |

[04 §4](../../milestones/01/04-verification.md#4-ci-與真機-runner) 對正式出口的 VM 限制仍適用；[D-25](../../.agents/notes/decisions/2026-09-27-d25-vm-first-automation.md) 允許先在 VM 演練登入與圖形流程，但結果只是開發證據，不能把這類演練誤寫成禁止執行，也不能直接升格為 G4 出口。D-47 只裁定 G3，不自動放寬 G4。既有實體證據保留原日期、head 與條件；舊 head 的通過不等於 G4 凍結版本已重驗。各出口按驗收矩陣組合所需證據，不以環境標籤一概否定單元／契約結果，也不把單一環境當成全項通過。

## 2. 量測安排

1. **基線**：功能開發期間可以先跑 NFR 與分層資源，找出差距；這些數字標為基線，不作出口。
2. **凍結**：功能凍結後在單一 commit 上取得所有出口數字（NFR-01～16、19.1 四態、8 小時長跑、AT 完整回歸）。凍結後任何修正都要重跑受影響的量測。
3. **條件**：冷登入 → 暖機 5 分 → 採樣 10 分，至少 3 次；PSS 取自 `smaps_rollup` 且不與 RSS 相加；版本指紋、PID／cgroup 與排除清單一併保存。
4. **未達標**：先分析原因與修正；仍未達標時提出數據與調整提案，由 owner 核定並寫成決策紀錄，核定前維持未通過。

## 3. AT 完整回歸（#56）

- 為 AT-01～32 逐項指定入口命令、證據環境與 oracle，形成可重跑清單；功能測試必須檢查實際狀態，不只看 Agent 回覆。
- 需要座位的情境（中文輸入、雙螢幕、錄影、reduced motion）列出手動步驟，由 owner 執行並記錄。
- 語意任務集依 D-43 規則重跑兩組並記錄模型版本，保留集降幅超過 5 pp 視為過擬合。
- 沒跑的情境標「未跑」，不推定通過；失敗保留 `session_id`／`change_id`／`operation_id`。

## 4. nightly 與 CI

- `nightly-refmachine.yml` 擴充到 G2、G3 的參考機項目；救援、鎖定、熱插拔從資訊性步驟改為必要步驟前，先確認參考機可穩定執行。
- 連續五個不同夜晚的結果作為 G1 EX1-15 的補件。
- 必要檢查與分支保護：先試設定；若 API 回 403 或方案限制，照實記錄並提出替代（例如合併前人工核對清單）。
- 參考機需要真正的「Ditto (Wayfire)」登入工作階段才能跑座位測試；自動登入不解鎖鑰匙圈的處理見 #44。

## 5. 安全與發行檢查

- 秘密外洩掃描（#59）列入階段出口；注入測試金鑰後掃描日誌、匯出、診斷包、崩潰報告、對話、生成產物與 store，命中應為 0。
- 發行審查（#51、#60）依 `ditto-release-audit` 第 7 步抽樣驗證；名稱與角色素材必須有書面結論，文件不得暗示法律審查已完成。
