# 01｜G0 範圍界線與出口門檻

> 本文回答兩件事：G0 做什麼、不做什麼；以及做到什麼程度才算通過。門檻一律寫成**可判定**的形式——有明確的量測方法、證據檔案與失敗判準。

## 1. G0 成立的三個條件

| # | 條件 | 反面（做到了但不算成立） |
| --- | --- | --- |
| A | 原生應用真的可控 | 能力目錄列出了 `desktop.windows.move`，但合成器其實不支援，呼叫後回成功而視窗沒動 |
| B | 合成器缺口有書面結論與決策 | 「試過了，大致可用」——沒有逐協定的探針輸出，沒有 D-02 決策紀錄 |
| C | 量測數字誠實且可重現 | 在開發筆電上跑一次，報 RSS，把合成器排除在統計範圍外 |

## 2. 範圍內

G0 交付以下能力，且**只交付以下能力**：

| 群 | 內容 |
| --- | --- |
| 平台 | 單一發行版／核心／GPU／驅動的支援矩陣與可重建映像；Qt／Quickshell／Rust／Node／pnpm 版本凍結；實體參考機與 nightly runner |
| 合成器 | 逐協定的能力探針套件、能力差異表、缺口處理方案、合成器決策（D-02） |
| Core | 倉庫骨架與 CI；Rust-first 契約型別管線；最小 IPC（握手、版本協商、事件序號與快照重連、取消與逾時）；呼叫身分綁定骨架；視窗／工作區／輸出轉接（讀取＋少量命令） |
| Shell | 可登入的 Quickshell 工作階段：背景、layer-shell 面板、Dock、工作區指示、執行中視窗清單；角色層與本機動畫；alpha 命中區 |
| QA | PSS 分層量測工具與報告產生器；UI 重啟存活驗證；工具配額基線；幀時與熱路徑取樣 |

能力目錄的 G0 清單與每項的描述子見 [03 §3](03-core-and-contracts.md#3-g0-能力目錄)。

## 3. 範圍外

### 3.1 明確不做

LLM 與 Agent、Cordis 桌面宿主與任何插件、Profile／revision／SQLite、ChangeSet 交易、權限授予與秘密儲存、熱換等級、租約協定、生成與測試宿主、救援模式、組合中心／插件中心／變更歷史／個人化四個管理介面、i18n 完整支援、雙螢幕矩陣完整驗收。

### 3.2 會很想做但不能做的邊界案例

這些是 G0 期間最可能被「順手做掉」的事。每一項都會在 G1 造成返工或違反原則：

| 誘因 | 為什麼不行 | G0 的正確做法 |
| --- | --- | --- |
| 「面板位置總要存一下，加個小 JSON 就好」 | 建立了 Core 以外的配置寫入路徑，違反 `ditto-authority-boundaries` 的禁則 1 | G0 **不產生任何持久化配置**。面板位置等一律走啟動參數或程式內建預設；不寫入 `$XDG_CONFIG_HOME` 或任何使用者可編輯的檔案 |
| 「Shell 直接用 Qt 的視窗 API 比較快」 | 繞過能力契約，G1 換供應者時消費者跟著壞 | 一切視窗操作走 `desktop.windows.*`；QML 端沒有第二條路徑 |
| 「事件還沒做好，先每秒輪詢視窗清單」 | 違反 RUN-07，且會讓待機 CPU 基線失去意義 | 先做事件（見 [03 §4.5](03-core-and-contracts.md#45-事件流快照與重連)）。真的只有輪詢可取得的狀態，記錄理由並設上界 |
| 「裝個 Node 服務來橋接比較省事」 | G0 的桌面工作階段內不得有 Node 執行期，否則資源基線會包含一個 G0 根本還沒設計的程序 | Node 只用於契約型別產生與測試工具，不進桌面工作階段 |
| 「角色加一個思考動畫，展示起來好看」 | AVA-04 直接禁止用動畫表示不存在的任務狀態 | G0 只做待命／注視／點擊回彈；思考態只存在於明確標示的測試夾具中 |
| 「順手把 `dittoctl` 做成救援入口」 | 救援是 G1-PLAT-03／04，且救援能力清單是刻意最小的 | `dittoctl probe` 只做診斷與契約消費；文件不得暗示救援已開始 |
| 「這台開發機跑出來的數字先當基線」 | 換機器後的數字不可比，等於沒有基線 | 所有效能與資源數字只在實體參考機產生；VM 只跑非圖形測試 |

## 4. 出口門檻

九項，全部通過才算 G0 出口。「條件通過」可用於記錄缺口與解除時點，但不等於通過出口；若要改變出口範圍或門檻，須先依決策程序核定並回寫上位文件。每項的「證據」欄是實際檔案路徑，出口評審時逐項核對。

### EX-01 原生應用可控，且不支援的操作誠實回報

| 欄位 | 內容 |
| --- | --- |
| 判準 | 參考應用集合（瀏覽器、終端、編輯器各一，版本固定）× 操作集合（`list`／`get`／`focus`／`move`／`resize`／`set_state`／`close_request`）的矩陣中，每一格都有明確結果：成功且 `readback` 比對一致，或回傳 `unsupported`。**回成功但回讀不一致** 與 **靜默成功** 同列不通過 |
| 方法 | `tests/g0/window-matrix` 腳本在參考機上逐格執行，每格記錄請求、回應、回讀結果 |
| 證據 | `artifacts/g0/window-matrix-<run_id>.jsonl` ＋ 出口評審中的矩陣表 |
| 對應 | DES-01～03、AT-01（G0 基礎部分） |
| 負責 | CORE ＋ PLAT |

## 6. G0 結束時能主張與不能主張什麼

`ditto-prose-standard` 與 `ditto-verification-evidence` 對這件事有明確要求。G0 的成果很容易被寫成比實際更完整的樣子：

| 可以說 | 不可以說 |
| --- | --- |
| 「在參考平台上，Ditto 可以列舉並操作原生視窗；不支援的操作會明確回報」 | 「Ditto 桌面已可用」——沒有 Profile、沒有插件、沒有救援，AT-01 只通過 G0 基礎部分 |
| 「角色動畫在參考機達成幀時目標，且不經 IPC」 | 「NFR-05 已達標」——NFR-05 的完整驗收在 G4，G0 只是初測 |
| 「Core 與 Shell 的 PSS 初始值已量測並核定為預算」 | 「待機資源符合 600 MiB」——G0 量不到 Cordis 宿主與 Agent，全桌面數字不存在 |
| 「契約型別管線與能力目錄一致性在 CI 上成立」 | 「AT-27 通過」——AT-27 的首次通過階段是 G1 |
| 「合成器能力差異表已建立，決策已記錄」 | 「合成器相容性沒有問題」——差異表裡的每個缺口都仍是 G1 的成本 |
| 「身分無法自述的負例測試通過」 | 「權限模型已完成」——權限授予、撤銷與共用授權入口都在 G1／G2 |

同一條規則適用於 README、PR 描述與任何對外說明。
