# 05｜量測工具、驗證腳本與 CI

> 對應工作包：G0-QA-01～04。開工前讀 `ditto-verification-evidence`；預算定義本身見 `ditto-process-budget`。

G0 的量測工具不是收尾工作，而是交付物：19.1 的分層預算要在 G0 核定，而核定需要一個從第一天就存在、且報告格式正確的工具。

## 1. 量測工具規格（G0-QA-01）

`crates/ditto-measure`，Rust 二進位 `ditto-measure`。選 Rust 的理由是不為量測再引入第三套執行期——量測工具本身不應該出現在被量測的程序清單裡造成干擾。

### 1.1 程序發現

**以 cgroup 與 systemd 單元識別程序，不以程序名稱比對。**

| 方式 | 為什麼 |
| --- | --- |
| 讀 `systemd --user` 的單元／scope 與其 cgroup 路徑 | 名稱比對會漏掉改名的程序，也會讓「把某個程序移出統計範圍」變得太容易 |
| 每個 Ditto 程序在啟動時歸入具名單元 | 程序清單因此是宣告的，不是推測的 |
| 合成器與工作階段程序另行標記 | 它們在統計範圍**內**，這是刻意的（見 `ditto-verification-evidence` 的刻度範例） |

### 1.2 採集欄位

每個取樣點對每個程序採集：

| 欄位 | 來源 | 注意 |
| --- | --- | --- |
| `pss_kib` | `/proc/<pid>/smaps_rollup` 的 `Pss` | **不得與 RSS 相加** |
| `rss_kib` | `/proc/<pid>/status` 的 `VmRSS` | 只作診斷用，不作預算判定 |
| `cpu_pct` | `/proc/<pid>/stat` 的兩次差分 | 標明採樣間隔 |
| `threads`、`fds` | `/proc/<pid>/status`、`/proc/<pid>/fd` | 洩漏診斷 |
| `cgroup` | `/proc/<pid>/cgroup` | 對應單元 |
| `cmdline` | `/proc/<pid>/cmdline` | 報告可讀性 |
| Node 專屬（未來） | `heapUsed`／`external`／`arrayBuffers` | **三者不得相加當作程序記憶體**；G0 無 Node 程序，欄位先保留 |
| GPU | 依 GPU 廠商工具（實際可用者於 G0-PLAT-01 決定） | 取不到就**標明取不到**，不得省略欄位 |

### 1.3 輸出

兩種輸出，一份原始一份報告：

```jsonc
// artifacts/g0/measure-<run_id>.jsonl —— 每行一個取樣點
{ "run_id": "2026-10-14T09:00:00Z-a3f",
  "ts": "2026-10-14T09:14:03+08:00",
  "state": "desktop_full_no_agent",       // 見 §3 的狀態標籤
  "fingerprint": { "kernel": "...", "qt": "...", "quickshell": "...",
                   "compositor": "...", "rust": "...", "node": "...",
                   "ditto_commit": "..." },
  "processes": [ { "unit": "ditto-core.service", "pid": 1234,
                   "pss_kib": 54210, "rss_kib": 71880, "cpu_pct": 0.4, ... } ],
  "excluded": [ { "unit": "firefox.scope", "reason": "user-opened application" } ],
  "gpu": { "available": false, "reason": "no vendor tool on reference GPU" } }
```

報告產生器輸出 `artifacts/g0/resource-report-<run_id>.md`，內容固定包含：版本指紋、狀態標籤、分層表（中位數／p95／峰值）、**完整程序清單**、**排除清單**、3 次重複的個別結果、量測條件。

### 1.4 排除清單的規則

可以排除：使用者自己開的瀏覽器與編輯器、既有 OS 基礎服務、本機模型權重。

**不可以排除**：Ditto 新增的任何背景服務、合成器、Shell、Core。

報告產生器要把排除清單做成顯式輸入（一個列表檔），而不是在程式碼裡寫死過濾規則——顯式輸入才能在 review 時被看見。

## 2. 量測流程（G0 適用版）

流程固定，缺一項就不是有效量測：

| 步驟 | 內容 |
| --- | --- |
| 1 | 冷登入參考機（不是從休眠恢復） |
| 2 | 暖機 5 分鐘：啟動參考應用集合並執行一組固定操作 |
| 3 | 採樣 10 分鐘，取樣間隔固定（建議 5 秒） |
| 4 | 報穩態中位數、p95、峰值；**穩態門檻以 p95 判定** |
| 5 | 至少重複 3 次，三次的結果全部列出，不只列平均 |
| 6 | 固定變因：桌面元件、背景、角色素材、開啟的應用與其內容 |
| 7 | 記錄版本指紋、PID 與 cgroup 對應、採樣期間 |

G0 的固定變因清單要寫進 `tests/g0/measure/profile.md`，之後每個階段沿用同一份，否則跨階段數字不可比。

## 3. G0 能量到什麼、量不到什麼

這一節是 EX-05 的誠實界線。報告必須分列狀態標籤，而 G0 只有其中兩個可以產生真實數字：

| 狀態標籤 | G0 可量測？ | 說明 |
| --- | --- | --- |
| `rescue_no_node` | **否** | 救援模式是 G1-PLAT-04 的交付物；G0 沒有救援模式 |
| `desktop_full_no_agent` | **部分** | G0 有 Core、Shell、合成器；**沒有 Cordis 宿主**。因此這個數字是「G0 子集」，不是 19.1 定義的完整桌面 |
| `agent_warm` | **否** | 沒有 Agent |
| `active_work` | **否** | 沒有重型工作 |

因此 G0 的資源報告必須在標題與每張表上標明「G0 子集」，並明確列出尚未包含的程序。把 G0 的數字寫成「全桌面 ≤600 MiB 已達標」是這個專案明令禁止的報告方式。

G0 能核定的預算分項因此只有兩項：

| 分項 | 19.1 初始目標 | G0 能做的事 |
| --- | --- | --- |
| Rust Core 與基本內建服務 | ≤80 MiB | 量測並核定初始值 |
| Quickshell UI 與預設角色 | ≤250 MiB | 量測並核定初始值；另測「角色關閉」與「減少動畫」兩組 |
| Cordis 宿主／Agent／全桌面 | — | **明確標記為本階段不可量測**，留待 G1／G2 |

超標的處理只有一條路：記錄數據 → 分析來源 → 提出調整提案 → 決策核定並留紀錄。不得改變暖機條件、不得把程序移出範圍、不得直接把門檻改成當前數字。

## 4. 幀時取樣（G0-QA-04）

| 項目 | 做法 |
| --- | --- |
| 主要來源 | Shell 內的 `FrameProbe.qml`：以 Qt Quick 的逐幀回呼記錄相鄰幀間隔，寫入 JSONL |
| 交叉驗證 | 若 [02](02-platform-and-compositor.md) 的 C-12（`wp_presentation`）可用，以呈現時間戳交叉比對，確認取樣沒有系統性偏差 |
| 互動腳本 | 固定四段：角色待命 10 秒、游標掃過角色 10 秒、拖曳一個視窗 10 秒、切換工作區 5 次 |
| 判準 | 每段各自計算：≥95% 的幀 ≤16.7 ms；3 次重複取 p95 |
| 同時採集 | §7 的 RPC 計數，兩者寫入同一個 `run_id`；記錄四段及 5 次明確切換命令的時間邊界，分開統計動畫期間與語意命令的請求 |
| 未達標 | 提出數據與原因（哪一段、哪些幀、GPU 或 CPU 瓶頸），不得縮短腳本或換機器重測 |

## 5. UI 重啟存活驗證（G0-QA-02）

`tests/g0/shell-restart-survival`：

| 步驟 | 內容 |
| --- | --- |
| 1 | 啟動參考應用集合；在編輯器中建立**未儲存**的緩衝，記錄其內容雜湊 |
| 2 | 記錄所有參考應用的 PID |
| 3 | 重啟 Shell：正常結束 10 次、`SIGKILL` 10 次，交錯執行 |
| 4 | 每次重啟後檢查：PID 全部存活、視窗仍可由 `dittoctl probe windows` 列舉、編輯器緩衝雜湊不變 |
| 5 | 記錄每次的重啟耗時（供 NFR-08 的 G1 版本參考，G0 只記錄不設門檻） |

任何一次 PID 消失或雜湊改變即 EX-03 不通過。**不接受「偶發」結案**——失敗要能從日誌的關聯欄位定位。

## 6. 工具配額基線（G0-QA-03）

G0 沒有工具與測試宿主，但配額機制要先驗證可用，否則 G3 才發現平台做不到會很貴。

| 步驟 | 內容 |
| --- | --- |
| 1 | 以 `systemd-run --user --scope` 建立受限 scope，設定 `MemoryMax`、`CPUQuota`、`TasksMax` |
| 2 | 記憶體案例：在 scope 內配置超過上限，驗證**只有該 scope 內的程序被終止**，桌面、Core、Shell 與參考應用不受影響 |
| 3 | CPU 案例：在 scope 內跑滿 CPU，驗證配額生效且桌面互動仍可用（幀時不崩） |
| 4 | 程序數案例：在 scope 內大量 fork，驗證 `TasksMax` 生效 |
| 5 | 記錄各工作類型的建議初始值：生成測試宿主、建置工作、一般工具 |
| 6 | 記錄 §8 提到的平台事實（cgroup v2、委派設定、Landlock ABI） |

產出 `docs/platform/resource-quota-baseline.md`，與 EX-05 的決策紀錄一併核定。

**要驗證的重點是「候選 OOM 不得連帶終止桌面」**，這是 19.1 與 SEC-12 的共同要求，也是 G3 隔離設計的前提。

## 7. RPC 計數與熱路徑

見 [04 §7](04-shell-and-avatar.md#7-熱路徑的機械化驗證ex-04-的第二條判準)。QA 側的責任是把它接進幀時腳本並納入 nightly，讓它在未來被破壞時當晚就被發現，而不是在 G4 的效能收斂時。

## 8. 測試分層（G0）

| 層 | 內容 | 執行 | 阻擋合併 |
| --- | --- | --- | --- |
| 單元 | Rust crate、TS 套件 | PR | 是 |
| 契約（跨語言） | 共享測試向量、錯版拒絕、亂序、重連 | PR | 是 |
| Schema 新鮮度 | 重新產生後無差異 | PR | 是 |
| 能力目錄一致性 | [03 §2.2](03-core-and-contracts.md#22-能力目錄是資料不是文件) 的四項 | PR | 是 |
| 身分負例 | [03 §5](03-core-and-contracts.md#5-呼叫身分綁定g0-core-04) 的三項 | PR | 是 |
| 授權掃描 | 依賴授權清單 | PR | 否（出口評審檢查） |
| 轉接整合 | 能力 × 參考應用矩陣 | nightly（真機） | 否 |
| 重啟存活 | §5 | nightly（真機） | 否 |
| 幀時與熱路徑 | §4、§7 | nightly（真機） | 否 |
| 資源量測 | §2 | 每週（真機） | 否 |
| 輸入法 | 人工＋腳本 | 階段出口 | 是（EX-08） |

分界判準：**需要真實合成器、真實應用或真實硬體的，不能進 PR 快檢**；其餘全部進，而且要擋合併。

## 9. 證據存放與命名

| 類型 | 路徑 | 進版控？ |
| --- | --- | --- |
| 原始取樣 | `artifacts/g0/<kind>-<run_id>.jsonl` | 否 |
| 報告 | `artifacts/g0/<kind>-report-<run_id>.md` | 否 |
| 平台文件 | `docs/platform/*.md` | 是 |
| 決策紀錄 | `.agents/notes/decisions/YYYY-MM-DD-<slug>.md` | 是 |
| 出口評審 | `.agents/notes/gate-reviews/G0-exit.md` | 是 |

`run_id` 格式 `<ISO8601 UTC>-<commit 前 3 碼>`，同一次量測的所有檔案共用同一個 `run_id`。CI 產生的 artifacts 保留期至少到 G1 結束——出口評審要能重新打開它們。

**門檻結果不得只寫「通過」**：每一項都要附量測條件與原始資料位置。失敗要能以 `session_id`／`change_id`／`operation_id`（G0 只有前者與請求 id）回溯到日誌。
