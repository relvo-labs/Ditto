# 02｜平台凍結與合成器能力盤點

> 對應工作包：G0-PLAT-01～05。本文給的是凍結哪些維度、探針怎麼設計、差異表長什麼樣、以及 D-02 在什麼條件下該選哪個答案。

## 1. 為什麼凍結要排在第一週

G0 之後的每一個數字——幀時、PSS、啟動時間、Landlock 能否 `full` 強制執行——都只在某個確定的平台組合上成立。平台沒凍結就開始量測，等於沒有量測；`ditto-verification-evidence` 把「換機器後的數字不可比」列為明確的判準。

凍結也不只是寫下版本號。**可重建**才是要求：半年後有人要復現 G0 的某個數字，必須能重建同一台機器。

## 2. 凍結維度（G0-PLAT-01）

| 維度 | 要記錄的內容 | 為什麼這一項會影響後續 |
| --- | --- | --- |
| 發行版與版本 | 名稱、版本、套件快照日期或 repo 快照 URL | 決定 Qt／wlroots／fcitx5 的可得版本 |
| 核心版本 | `uname -r`、設定檔中的 LSM 清單 | **Landlock ABI 版本決定沙箱能否 `full` 強制執行**（R-16、G3 前置） |
| CPU／RAM／儲存 | 型號、核心數、記憶體、SSD 型號 | 19.1 的參考機定義為 4 核／16 GB／SSD |
| GPU 與驅動 | 廠商、型號、驅動與 Mesa 版本 | 決定用哪個 GPU 量測工具，以及顯存能不能讀到 |
| 顯示 | 1080p 60 Hz 為主測；雙螢幕與縮放組合另記 | NFR-05 的幀時判準綁定刷新率 |
| 合成器 | 名稱、版本、commit、啟用的外掛清單 | 差異表的每一列都綁定這個版本 |
| 工作階段 | 登入管理器、`systemd --user` 是否可用、環境變數集合 | 監督機制與工作階段安裝（G1／G4）依賴它 |

產出兩份東西：

1. `docs/platform/support-matrix.md` — 上表的實際值，每個值附取得方式（指令或檔案路徑）。
2. `packaging/reference-image/` — 可重建的安裝腳本或映像定義，含套件清單與其版本雜湊。**「照著文件手動裝」不算可重建。**

### 2.1 參考應用集合

EX-01 與 EX-03 都要用到，必須同時凍結版本：

| 角色 | 選擇判準 | 為什麼需要它 |
| --- | --- | --- |
| 瀏覽器 | 原生 Wayland 執行、多視窗、有 XWayland 對照組 | 最重的視窗管理案例 |
| 終端機 | 輕量、啟動快、可程式化輸入 | 重啟存活測試的高頻案例 |
| 編輯器 | **有未儲存緩衝的概念**、可從外部檢查緩衝內容 | EX-03 的未儲存內容保留判準要靠它 |

編輯器的選擇要特別注意：它必須讓測試腳本能在 Shell 重啟後**驗證緩衝內容未變**（例如透過其 swap／session 檔或 CLI）。選一個做不到這件事的編輯器，EX-03 就只能驗 PID 存活，門檻會被迫放寬。

## 3. 工具鏈凍結（G0-PLAT-02）

| 工具 | 凍結方式 | 檔案 |
| --- | --- | --- |
| Rust | 固定 stable 版本 | `rust-toolchain.toml`（`channel`、`components`、`targets`） |
| Cargo 相依 | lockfile 進版控 | `Cargo.lock` |
| Node | 單一 LTS，同時用於型別產生與測試工具 | `.nvmrc` ＋ `package.json` 的 `engines` |
| pnpm | 固定版本 | `package.json` 的 `packageManager` |
| Qt／Quickshell | 版本＋commit；記錄用到的 QML 模組與其可得性 | `docs/platform/support-matrix.md` |
| 合成器 | 版本＋commit＋外掛清單 | 同上 |

兩點約束：

- **Node 版本要與未來 vendored Cordis 相容。** 上游 harness 的 `engines` 是 `^22.19.0 || >=24.0.0`；G0 選版時就把這個區間納入，否則 G1 引入 Cordis 時要重凍一次。
- **G0 的桌面工作階段內不得有 Node 執行期。** Node 只出現在建置期與測試工具；資源報告的程序清單裡不應該有它。

## 4. 合成器能力盤點（G0-PLAT-03）

### 4.1 探針要合成器中立

這是本工作包最重要的設計決定。R-01 的備案是「改採 Sway 或 Hyprland」，而備案的成本完全取決於探針能不能直接在另一個合成器上重跑。

因此探針套件的要求是：

- 只依賴 Wayland 協定與標準介面，**不依賴任何合成器專屬 IPC**（專屬 IPC 的探測另列為獨立項目，標記其綁定的合成器）。
- 每個探針輸出結構化 JSON，不是人讀的日誌。
- 一鍵執行：`tools/compositor-probe/run.sh <compositor-label>` 產出單一 JSON。
- 換合成器時只換 `<compositor-label>`，不改探針程式碼。

做到這三點，合成器切換的成本從「重做盤點」降為「重跑一次」。

### 4.2 兩層探測

| 層 | 做什麼 | 為什麼不夠／為什麼需要 |
| --- | --- | --- |
| 全域列舉 | 列出合成器公告的所有 Wayland global 與版本 | 快、可完全自動化；但**公告存在不等於實作完整** |
| 功能探測 | 對每項能力實際執行一次最小操作並驗證結果 | 慢、要寫程式；但這是唯一能分辨「支援」與「部分支援」的方法 |

**只做全域列舉就填差異表是不合格的盤點。** 差異表的「部分支援」一欄若永遠是空的，通常代表功能探測沒做。

### 4.3 協定與能力清單

每一列都要跑功能探測。嚴重度欄位定義：**阻斷**＝缺這項則該合成器不可用；**需轉接**＝協定不提供，必須另尋路徑；**記錄**＝G0 只記錄事實，缺口在後續階段處理。

| # | Ditto 需要的能力 | 候選協定／介面 | 功能探測 | 嚴重度 | 對應需求 |
| --- | --- | --- | --- | --- | --- |
| C-01 | 面板與 Dock 掛載 | `zwlr_layer_shell_v1` | 建立四個 layer 各一個表面；設定 anchor、exclusive zone、keyboard interactivity；驗證其他視窗確實避開 exclusive 區域 | 阻斷 | DES-05 |
| C-02 | 視窗列舉與中繼資料 | `zwlr_foreign_toplevel_management_v1`／`ext_foreign_toplevel_list_v1` | 開三個應用，驗證 title、app_id、state 的事件是否即時且完整 | 阻斷 | DES-02、DES-03 |
| C-03 | 視窗控制（聚焦、關閉、最大化、最小化） | 同 C-02 的 management 協定 | 逐一送出請求並以 C-02 的事件回讀 | 阻斷 | DES-03 |
| C-04 | **視窗移動與調整大小** | 上述協定**不提供座標操作** | 探測合成器專屬 IPC 或外掛是否提供；若無，記為需轉接並估成本 | 需轉接 | DES-03 |
| C-05 | 工作區列舉與切換 | `ext_workspace_v1` 或合成器專屬 IPC | 建立／切換／列舉；驗證事件 | 需轉接；無可行路徑時阻斷 | DES-04 |
| C-06 | 輸出列舉、縮放與熱插拔 | `wl_output` v4、`xdg_output` | 列舉；模擬拔除（或以 `wlr-randr` 等工具停用輸出），驗證事件與視窗重新定位 | 阻斷 | DES-08 |
| C-07 | 命中區與點擊穿透 | `wl_surface.set_input_region` | 設定非矩形 input region，在透明區點擊，驗證事件到達下層應用 | 阻斷 | AVA-05 |
| C-08 | 中文輸入 | `text_input_v3` ＋已驗證的合成器輸入法 bridge | 見 §6；Wayfire 採 `input-method-v1`，見[決策紀錄](../../.agents/notes/decisions/2026-09-23-g0-input-method-bridge.md) | 阻斷 | DES-07 |
| C-09 | 焦點轉移 | `xdg_activation_v1` | 從啟動器啟動應用後，驗證新視窗取得焦點 | 需轉接 | DES-02 |
| C-10 | 工作階段鎖定 | `ext_session_lock_v1` | 列舉與最小鎖定流程 | 記錄 | DES-06、SEC-08（G1） |
| C-11 | 截圖與螢幕分享 | `wlr_screencopy`、xdg-desktop-portal | 列舉後端與可用介面 | 記錄 | DES-11（P1） |
| C-12 | 呈現時間戳 | `wp_presentation` | 取得一次 presentation feedback | 記錄 | 幀時交叉驗證（[05 §4](05-measurement-and-verification.md#4-幀時取樣g0-qa-04)） |
| C-13 | XWayland 應用 | — | 以 XWayland 應用重跑 C-02／C-03 | 記錄 | 應用相容性 |
| C-14 | 閒置與抑制 | `ext_idle_notify_v1` | 列舉 | 記錄 | 未來電源整合 |

C-04 值得特別說明：`wlr-foreign-toplevel-management` 提供的是 activate／close／maximize／minimize／fullscreen 這類狀態操作，**不含座標移動**。因此「視窗移動」在任何以該協定為基礎的方案上都會落在「需轉接」，這不是某個合成器的缺陷，而是協定範圍問題。G0 的任務是查清楚這條路走不走得通、走得通要花多少，而不是假設它會有。

### 4.4 專屬 IPC 的探測

多數 wlroots 系合成器另有自己的 IPC（socket＋JSON 或自訂協定），常常正是 C-04、C-05 的唯一解。探測方式：

1. 確認該版本是否內建該 IPC（外掛是否需另外啟用、是否在凍結的發行版套件中）。
2. 列舉其可用命令與事件。
3. 對 C-04、C-05 實際執行一次並回讀。
4. 記錄其**穩定性承諾**：是否為公開契約、版本間是否可能改變。

結論寫進差異表時要分清楚：經由專屬 IPC 達成的能力，其 `provider` 綁定該合成器，換合成器時要重寫——這是 D-02 決策時必須看到的成本。

### 4.5 能力差異表

產出 `docs/platform/compositor-capability-matrix.md`，每列格式固定：

```markdown
| 能力 | 協定／路徑 | 判定 | 證據 | 缺口處理方案 | 估計成本 | 綁定合成器 |
```

四態定義（**不得自創第五態**）：

| 判定 | 意思 |
| --- | --- |
| 支援 | 功能探測完全通過，行為符合協定語意 |
| 部分支援 | 探測通過但有行為差異或限制，且**差異已寫明** |
| 不支援 | 協定不存在，或存在但探測失敗 |
| 需轉接 | 協定不涵蓋此能力，必須經專屬 IPC、合成器外掛或自寫轉接達成 |

「部分支援」若沒有寫明差異，視同未完成盤點。

## 5. D-02 合成器決策（G0-PLAT-03 的出口）

### 5.1 預先承諾的判準

判準必須在探測**之前**寫定，否則會變成「拿到結果再找理由」。G0 啟動評審須從 Sway／Hyprland 預選備案合成器並記錄理由，同時確認以下規則；未核定前是提案，不能依探針結果事後調整判準。確認後寫入 D-02 決策紀錄的「依據」欄：

| 條件 | 結論 |
| --- | --- |
| C-01、C-02、C-03、C-06、C-07、C-08 全部「支援」，且 C-05 有可行路徑、轉接成本 ≤2 人週 | **維持首選合成器**。C-04、C-05 所需轉接的成本計入 G1 |
| 上述六項任一為「不支援」，或「部分支援」但未通過下述最低行為驗證 | **換合成器**。不接受以自寫合成器外掛補阻斷級缺口 |
| 上述六項為「部分支援」，且差異表證明最低行為仍全部成立 | 可維持首選合成器；D-02 必須逐項列出限制與後續成本，不得把「部分支援」改寫為「支援」 |
| C-05 需轉接且估計成本 > 2 人週 | 升級為決策點：比較「自寫轉接」與「換合成器後重跑探針」的總成本，取低者 |
| C-04 需轉接且只能經專屬 IPC | 可接受，但必須在差異表標記綁定關係，並在 G1 的能力描述子中如實反映其可用條件 |
| 首選合成器的 C-05 沒有可行的列舉、切換與事件路徑 | 先在備案合成器上重跑探針，D-02 時比較可行性與成本 |
| 首選與備案的 C-05 都沒有可行路徑，或兩者都有其他阻斷級缺口 | 先於 D-02 記錄第三候選能否解決缺口；若仍無可行方案，觸發範圍決策，把受影響能力列為 `unsupported` 並提出 MVP 範圍調整，走 `ditto-decision-record`。**不得**靜默縮小 DES-03／04 的範圍 |

「部分支援」的最低行為以 §4.3 的功能探測為準：C-01／02／03／06／08 必須完成各列所述操作與回讀；C-07 必須證明透明區點擊到達下層、不透明區點擊由角色接收，且被遮擋時仍能以快捷鍵喚回。多矩形近似只有在這些測試都通過時才可接受；單一矩形若攔截透明區，不能算通過。C-05 成本超過 2 人週時，即使六項最低行為都通過，仍須執行成本比較，不能直接套用「維持首選」結論。

### 5.2 時點

| 時點 | 事件 |
| --- | --- |
| W3 結束 | 首選合成器的探針結果出齊，差異表初版；阻斷級缺口須立即通報 |
| W3～W4 | 若觸發換合成器條件，依 [07 §3](07-decisions-and-risks.md#3-換合成器的觸發與代價) 在備案合成器上重跑探針並比較兩份差異表 |
| **W4 結束** | **D-02 必須決策並寫入紀錄**。逾期即阻擋 G0 出口 |

### 5.3 備案成本

切換合成器的實際成本（用於 5.1 的比較）：重跑探針約 2 天；`ditto-compositor` 的協定實作大部分可沿用（同為 Wayland 協定）；專屬 IPC 相關的部分重寫；Shell 端的 layer-shell 使用方式通常不變。`milestones/01/05 §3.2` 假設「若需自寫轉接，G1 增加 6–10 人週」——這個數字在 D-02 決策時以差異表的實際缺口重新估算並回寫。

## 6. 輸入法鏈路（G0-PLAT-04）

| 步驟 | 內容 |
| --- | --- |
| 1 | 確認輸入法框架版本與 Wayland 後端（`text_input_v3` 或 `input_method_v2` 路徑），記錄其對合成器的要求 |
| 2 | 設定工作階段環境變數（`XMODIFIERS`、`QT_IM_MODULE` 等，實際需要哪些依框架而定，一併記錄） |
| 3 | 在 QML 文字輸入元件驗證：切換輸入法、輸入中文、候選視窗位置、送出、退格 |
| 4 | 在參考終端與參考編輯器重複同一組操作 |
| 5 | 驗證文字剪貼簿在三者之間互通 |

產出 `docs/platform/input-method-report.md`，含逐步驟結果與失敗項的處理方案。候選視窗位置錯誤是最常見的問題，通常來自合成器或 Qt 的游標矩形回報——若無法修正，記為「部分支援」並在 EX-08 判定時說明影響範圍，**不得直接標記通過**。

## 7. 真機 runner（G0-PLAT-05）

| 項目 | 要求 |
| --- | --- |
| 硬體 | 與支援矩陣完全一致的實體機。**取得可能有交期，列為 W1 的第一件事** |
| 註冊 | 註冊為 CI 的 self-hosted runner，標籤明確（例如 `ditto-refmachine`） |
| 工作流 | nightly：執行 EX-01／03／04 的腳本並上傳 artifacts；每週：執行完整量測流程 |
| 指紋 | 每次執行開頭輸出版本指紋（核心、Qt、合成器、Rust、Node、Ditto commit），寫入 artifact |
| 邊界 | 圖形與效能測試**只**在這台機器上跑；VM 上只跑契約測試、單元測試與 schema 新鮮度 |
| 降級 | 硬體未到位期間，允許在 VM 上開發與跑非圖形測試，但**任何數字都不得進入出口評審**；此狀態要在每週進度中明示 |

## 8. 平台事實記錄（給 D-06 與 R-16）

G0 不做沙箱，但要把後續階段依賴的平台事實記錄下來，因為它們綁定在凍結的核心版本上：

| 事實 | 取得方式 | 誰會用到 |
| --- | --- | --- |
| Landlock ABI 版本與可用性 | 核心版本、`/sys/kernel/security/lsm`、實際 syscall 探測 | G3 的隔離；R-16 的 `partial` 風險 |
| cgroup v2 是否可用、`systemd --user` 的委派設定 | `/sys/fs/cgroup`、`systemctl --user show` | G0-QA-03 的配額基線；G1 的資源配額施加 |
| `bwrap` 可用性與版本 | 套件版本 | G3 |
| 秘密儲存服務（Secret Service／keyring）可用性 | D-Bus 介面列舉 | G2 |

記錄進 `docs/platform/support-matrix.md` 的獨立小節。**只記錄事實，不在 G0 對它們做設計決定。**
