# Ditto 文案與文件標準

> 產品文案與專案文件的語氣分層與誠實要求。

## Overview

Ditto 的文字有兩種讀者同時存在：想把桌面改成某個樣子的使用者，以及要排查問題的工程師。把兩者混在同一段裡，結果是使用者看不懂、工程師找不到需要的 ID。

另一半的問題是分寸。這個專案有大量**尚未驗證**的目標與**刻意不做**的範圍，文件一旦把目標寫成事實、把原型成果寫成原生能力，後續每份文件都會繼承那個錯誤。

## When to Use

用於：UI 字串、錯誤訊息、變更摘要、狀態文字、對話回覆語氣、README 與 `docs/` 頁面、PR 描述、發行說明。

不適用：

- 某項宣稱背後的證據夠不夠 → `ditto-verification-evidence`。本 skill 管怎麼寫，那個 skill 管能不能寫。
- 決策落定的紀錄格式 → `ditto-decision-record`。

## Workflow

### 1. 判斷讀者層

| 層 | 內容 | 放哪裡 |
| --- | --- | --- |
| 產品層 | 使用者的目標與看得見的結果 | 一般流程、變更卡、對話、通知 |
| 診斷層 | 契約 ID、程序資訊、原始錯誤、日誌、堆疊 | 可展開的診斷區、日誌、`dittoctl` 輸出 |

判準：**使用者不需要知道這個名詞就能完成工作嗎？** 需要知道才能完成 → 產品層，用產品語言。不需要 → 診斷層。

產品層說「工作列位置」「影響中的工作」「這個組合已保存」；不說 `dock.position`、`capability_id`、`fiber state PENDING`。

診斷層不做相反的事：**不要為了好看而美化錯誤**。診斷區要有精確的 ID 與原始訊息，那是它存在的理由。

### 2. 寫狀態文字

狀態必須對應真實階段，且**文字與視覺同時表達**（不靠動畫或顏色單獨傳達）。

- 只在真的在做那件事時顯示那個階段。任務已停止就不得繼續顯示思考動畫。
- 長於 1 秒的本機工作顯示實際狀態，不顯示無意義的通用等待語。
- 模型延遲與本機延遲分開表達，不要把「模型正在回應」寫成「正在套用」。

### 3. 寫結果

四種結果各有寫法，對應 `ditto-changeset-transaction` 的判定：

| 結果 | 寫法要點 |
| --- | --- |
| 成功 | 說明改了什麼，給撤銷入口 |
| 失敗 | 說明失敗的是哪一步、目前狀態是否已回復、下一步可以做什麼 |
| 部分完成 | **逐項列出**哪些已生效、哪些未回復，不得用「大致完成」帶過 |
| 結果未知 | 明說不確定、說明正在如何確認，**不得**寫成成功或失敗 |

不支援的需求要說清楚缺少什麼能力，並提供組合、安裝或生成的可行路徑；不要只說「無法處理」。

### 4. 寫文件

四條規則：

1. **待驗證的目標寫成目標。** 資源與效能數字是驗收目標，不是已達成數據。寫「目標 ≤600 MiB，待 G1 量測」，不寫「記憶體占用 600 MiB」。
2. **不以原型成果冒充原生能力。** 前端原型驗證的是互動契約；它不代表原生效能、安全邊界或模型接入已成立。
3. **區分已完成與計畫。** 描述尚未實作的東西時，時態與措辭要讓讀者一眼看出。文件標題若是計畫，開頭就說它是計畫。
4. **已知限制要寫出來。** 誠實列出限制比省略更有用，且是發行交付物的要求項。

### 5. 語言與術語

| 元素 | 語言 |
| --- | --- |
| 產品文案與專案文件 | 繁體中文 |
| 程式碼、識別字、指令、路徑 | 英文 |
| 需求 ID、能力 ID、事件名 | 原樣（`CHG-04`、`desktop.windows.move`） |
| skill 的 `description` | 英文（跨語言可發現性） |

術語一致：同一概念全專案用同一個詞。「組合」不要有時寫成「配置」有時寫成「設定檔」；`Profile`、`ChangeSet`、`revision` 這類契約詞在中文句子裡保持原樣，不自創譯名。

### 6. 驗證

- 隨機抽一段產品層文案，確認其中沒有只有工程師看得懂的詞。
- 搜尋文件中的效能與資源數字，確認每個都標示為目標或附量測條件。
- 確認每份計畫型文件在開頭聲明自己是計畫。
- 確認錯誤訊息有下一步，不是只有錯誤本身。

## Calibrated Examples

| 情境 | 不要 | 要 |
| --- | --- | --- |
| 變更摘要 | 「已套用 ChangeSet cs-8841（3 ops committed）」 | 「已把工作列移到左邊，並關閉通知。可以撤銷。」診斷區另列變更 ID 與逐項操作 |
| 插件失敗 | 「Plugin load failed: FiberState.FAILED」 | 「『搜尋式啟動器』沒有啟動成功，已切回原本的啟動器。可查看診斷或重試。」 |
| 資源目標 | 「Ditto 待機占用 600 MiB」 | 「待機資源目標為全產品 PSS ≤600 MiB（Agent 已退出），待 G1 量測核定」 |
| 原型說明 | 「已支援對話改造桌面」 | 「前端原型已驗證對話改造的互動流程；原生控制、Cordis 與模型接入尚未實作」 |
| 結果未知 | 「安裝完成」／「安裝失敗」 | 「目前無法確認安裝是否完成，正在查詢實際狀態。請稍候，不要重複安裝。」 |
| 部分完成 | 「大致完成，少數項目未套用」 | 「工作列與布局已套用。通知設定未生效，已保留原設定。」 |
| 不支援 | 「這個需求無法處理」 | 「目前沒有能讀取行事曆的模組。可以安裝一個，或先用待辦面板替代。」 |
| 角色狀態 | 思考動畫持續播放（任務已停） | 任務停止時立即停止思考動作，並顯示實際狀態文字 |

**灰色地帶：技術詞什麼時候可以出現在產品層？** 判準是使用者是否已經在用這個詞思考。「工作區」「快捷鍵」「模組」使用者會用，可以出現。「供應者」「能力」「fiber」是實作詞彙，即使準確也不放產品層。若某個實作概念真的必須讓使用者知道（例如「安裝」與「啟用」是兩件事），那就用產品語言把它解釋清楚，而不是搬實作術語。
